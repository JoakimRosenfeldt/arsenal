Decision to approve

Approve one package of choices

Use Electron, React, strict TypeScript, Electron Forge, and Forge's stable Webpack template. Read a user-selected Rekordbox XML export into memory. Show Collection songs in a read-only, paged table.

The XML is a snapshot. Rekordbox changes appear only after the user exports again and imports the newer file.

Reply approve to authorize implementation. Until then, no scaffold, dependency install, or application source code will be created.

A live view of Rekordbox would require a different design based on its private encrypted database. This plan rejects that route for the first milestone.

First milestone

Included

  • Choose one local Rekordbox XML export.
  • Read Collection track metadata without changing the file.
  • Show title, artist, album, genre, BPM, key, and duration.
  • Sort once by artist and title, then page through the songs.
  • Show source name, import time, and song count.
  • Import a newer export during the same session.
  • Keep the current catalog visible if a later import fails.
  • Handle empty, cancelled, malformed, and unreadable files.

Deferred

  • Direct access to Rekordbox master.db.
  • Playlists, folders, cue points, beat grids, and waveforms.
  • Search, column sorting, filters, and configurable columns.
  • Editing metadata or writing anything back to Rekordbox.
  • Audio playback and access to music files.
  • A local database, metadata cache, or saved source path.
  • Accounts, cloud sync, telemetry, auto-update, and remote assets.
  • Signing and public distribution.

Use the documented XML export

Rekordbox 7.2.14 documents File > Library > Export Collection in xml format. The export contains Collection, playlist, and track information. Cloud Library Sync tracks that exist only on another computer or mobile device are omitted. The app will state that limitation next to its import instructions. Rekordbox 7.2.14 manual

The published XML format defines Collection TRACK fields such as title, artist, album, genre, duration, BPM, rating, file location, and tonality. The parser will map the small subset used by the table and ignore unknown attributes. Rekordbox XML format

Option What it gives us Cost Decision
XML export Documented, local, read-only input with a published shape. The user must export again to refresh the snapshot. Use now.
Private database Could reflect the installed library without manual export. Rekordbox 6 and 7 use an encrypted SQLCipher database. Existing readers are unofficial and version-sensitive. Reject for this milestone.
Local mirror Fast queries and persistence. Adds migrations, freshness rules, recovery, and another copy of the data. Add only after measured need.

The private database assessment is based on the independent pyrekordbox project, which describes itself as unofficial and documents the SQLCipher requirement.

Framework recommendation

Use React with strict TypeScript. The app starts as one table, but library management tends to grow into selection, filters, row actions, and detail panels. React handles that growth without requiring a server framework. Keep the renderer plain: one screen, local component state, semantic HTML, and one CSS file.

Use Electron Forge for development and packaging because Electron recommends it. Start from Forge's TypeScript and Webpack template. Forge still marks its Vite integration experimental, and this app gets little value from accepting that churn. Electron packaging guidance, Forge Webpack and TypeScript template, Forge Vite status

Choice Strength Why it loses or wins
React + TypeScript + Forge Webpack Stable Forge path and a good fit for a data-heavy screen. Wins on maintenance and future UI work. Webpack's slower development loop is acceptable here.
Svelte + TypeScript Less component code and a smaller renderer. Electron already dominates package size. The smaller runtime does not offset the less standard Forge path.
Vanilla TypeScript Fewest runtime dependencies. Starts smaller, then makes table state and later interactions manual.
React + Forge Vite Faster development startup. Forge labels the integration experimental. Revisit when that changes.

Initial dependencies stay narrow: React, React DOM, and one strict streaming XML parser. Use npm and commit the lockfile. Do not add a router, global state library, component kit, Tailwind, ORM, table framework, or virtualization package.

Runtime shape

Electron's main process owns every privileged action. It opens the native file dialog, reads the selected XML, normalizes songs, owns the in-memory catalog, and returns one page at a time. The renderer never sees XML, a full filesystem path, Node APIs, or Electron objects.

Runtime network access is unnecessary. Production content uses a restrictive content security policy, denies navigation, new windows, and permissions, and enables renderer isolation and sandboxing. Electron security checklist

Caller's view

const result = await window.djLibrary.importRekordboxExport();

if (result.kind === "imported") {
  const firstPage = await window.djLibrary.listSongs({

Contract sketch

type DjLibraryApi = Readonly<{
  status(): Promise<LibraryStatus>;
  importRekordboxExport(): Promise<ImportResult>;
  listSongs(page: PageRequest): Promise<SongPage>;
}>;

type SongRow = Readonly<{
  id: string;
  title: string;
  artist: string | null;
  album: string | null;
  genre: string | null;
  bpm: number | null;
  musicalKey: string | null;
  durationSeconds: number | null;
}>;

type CurrentCatalog = Readonly<{
  sourceName: string;
  importedAt: string;
  songs: readonly SongRow[];
}>;

The main process validates page limits. Song IDs need to be unique only within one import. A successful import replaces the catalog in one step. Cancellation or failure leaves the prior catalog untouched.

src/renderer/App.tsx Import instructions, feedback, summary, paging, and the song table.
src/renderer/app.css Plain responsive styles for the one screen.

Do not start with a worker. A streaming parser keeps memory bounded. If a representative export causes visible lifecycle stalls, move parsing to an Electron utility process or Node worker behind the same API.

Implementation plan after approval

  1. Secure Electron shell

    Create the Forge Webpack and TypeScript project, add React, and open one local renderer. Enable contextIsolation and sandboxing, disable Node integration, block unexpected navigation and permissions, and set a restrictive production content security policy. The outcome is an empty local app with no file access in the renderer.

  2. Rekordbox import boundary

    Add the native XML picker and a strict streaming parser. Accept DJ_PLAYLISTS/COLLECTION/TRACK, ignore playlists and unknown fields, reject DTDs, external entities, malformed XML, and wrong-root documents, normalize missing values to null, and build a new catalog before replacing the old one.

  3. Read-only song browser

    Render import guidance, loading and error feedback, the source summary, a semantic table, and previous and next page controls. Keep the page size fixed at 100. Sort the catalog once by artist and title. Do not add search, editing, playback, or saved settings.

  4. Verify and package locally

    Run type checking, linting, and a production package build. Compare the displayed count and sample fields with a real Rekordbox export. Exercise empty, malformed, cancelled, and failed replacement flows. Launch the packaged app offline and confirm that it makes no network requests. Do not add automated tests in this milestone.

Done means

  • A valid Rekordbox XML export opens through a native file dialog.
  • The displayed Collection count matches the export.
  • Every song can be reached through table paging.
  • Core fields match sampled Rekordbox rows.
  • The app never modifies the XML, audio files, or Rekordbox data.
  • Bad input produces a clear local error and no crash.
  • A failed replacement keeps the current catalog visible.
  • The packaged app works with networking disabled.

Risks and chosen responses

Risk Response
The view becomes stale after Rekordbox changes. Call it an imported snapshot in the UI. Require a new export and import.
Cloud-only tracks are absent. Show Rekordbox's documented limitation beside the import action.
The XML gains new fields. Read known fields, ignore unknown attributes, and keep the raw schema inside one parser.
A very large export blocks Electron's main process. Stream first and measure a real export. Add a worker without changing the renderer API only if needed.
Users expect the app to remember their file. Keep version one session-only. Add path persistence only after that behavior is requested.
Packaging scope expands into public distribution. Treat signing, notarization, and platform installers as a separate approved milestone.

Architecture synthesis

The base design is the session-only, main-owned paged catalog with React, TypeScript, Forge, and Webpack. It won because it keeps XML and filesystem policy behind three operations while avoiding an experimental build path.

  • Kept from the smallest snapshot design: explicit snapshot wording, the cloud-only warning, atomic catalog replacement, and IDs scoped to one import.
  • Kept from the paged design: main-owned paging and the rule that virtualization waits for measured lag.
  • Rejected: Forge Vite, a full-library IPC payload, saved settings, a local database, a worker before measurement, and renderer-visible service lifecycle events.
